FastAPI GenAI Service - System Design

How a prompt travels from the client to a TinyLlama model and back as a response. Current state: "Act 1 (naive)" - model is loaded on every request.

1. What this project is

A small web service that exposes one HTTP endpoint. A client sends a text prompt; the service runs it through a local open-source language model (TinyLlama/TinyLlama-1.1B-Chat-v1.0 from Hugging Face) acting as a "friendly tutor for school students", and returns the generated answer.

FileRole
main.pyThe web layer. Creates the FastAPI app and defines the /generate/text endpoint (the "controller").
models.pyThe AI layer. Knows how to load the model and how to turn a prompt into generated text.
genaiservice/The Python virtual environment holding fastapi, uvicorn, torch, transformers, etc. Not application code.

2. High-level architecture

Five layers, from outside to inside. Colors match the component cards below.

3. Components and what each one does

Client

Anything that can send an HTTP GET: a browser, curl, Postman, or FastAPI's built-in docs page at /docs. It supplies the prompt (and optionally temperature) as URL query parameters and receives the answer as JSON.

Uvicorn

The ASGI server process. It listens on a port (default 8000), parses raw HTTP, and hands the request to FastAPI. With --reload it also watches files and restarts on change.

FastAPI app (main.py)

Routes GET /generate/text to the handler function serve_language_model_controller. FastAPI automatically reads prompt (required string) and temperature (float, default 0.7) from the query string, validates their types, and converts the returned value to a JSON response.

Handler function

The "controller". It orchestrates: start a timer, call load_text_model(), call generate_text(...), print timings, return the text. It contains no AI logic itself.

load_text_model()

Builds a Hugging Face pipeline("text-generation") for TinyLlama: downloads weights on first use (cached afterwards in ~/.cache/huggingface), reads them into memory, and places them on the GPU or CPU.

generate_text()

Wraps the user prompt with a fixed system prompt, formats it using the model's chat template, runs generation (max 128 new tokens, sampling with top-k 50, top-p 0.95), and returns only the newly generated text.

Hugging Face pipeline / tokenizer

The tokenizer converts text to token IDs and back. The pipeline runs the tokens through the model repeatedly, producing one token at a time until it stops or hits the 128-token limit.

PyTorch and hardware

models.py picks cuda if a GPU is available, otherwise cpu. Dtype is bfloat16 on GPU (less memory, faster) and float32 on CPU (bfloat16 is poorly supported there). All the matrix math runs here.

4. Where the prompt is received and how the response is produced

Example request: GET http://localhost:8000/generate/text?prompt=What is gravity?&temperature=0.7

  1. Client sends the request. The prompt travels in the URL query string: prompt="What is gravity?", temperature=0.7.
  2. Uvicorn receives it on its TCP port, parses the HTTP request, and passes it into the FastAPI application.
  3. FastAPI routes it. The path /generate/text with method GET matches the decorator on line 9 of main.py. The query parameters are bound to the function arguments prompt and temperature (this is the exact point where the prompt enters your code). Because the handler is a plain def, FastAPI runs it in a worker thread so the server stays responsive.
  4. Model loading (slow step). The handler calls load_text_model(). A new pipeline is built: weights are read from the disk cache into RAM/VRAM. This repeats on every request.
  5. Prompt assembly. generate_text() builds a two-message list (the fixed system prompt plus the user prompt) and calls tokenizer.apply_chat_template(...). That produces the exact special-token-formatted string TinyLlama was trained on, ending with an "assistant's turn" marker.
  6. Tokenization and inference. The pipeline tokenizes the string, then loops: the model predicts a probability distribution over the next token, one token is sampled (using temperature, top-k, top-p), appended, and fed back in. This repeats until an end token or 128 new tokens.
  7. Decoding. Token IDs are converted back to text. return_full_text=False drops the input so only the answer remains; .strip() trims whitespace.
  8. Return path. The handler prints a timing line to the server console and returns the string. FastAPI serializes it to JSON, Uvicorn sends the HTTP 200 response, and the client sees the answer.

6. Runtime and deployment view

AspectCurrent design
Process modelOne Uvicorn process running one FastAPI app (started with something like uvicorn main:app --reload).
StateNone. The service is stateless: each request is independent and nothing is stored between calls (no chat history, no database).
Model storageWeights are downloaded once from the Hugging Face Hub into the local cache, then read from disk.
ComputeLocal GPU if CUDA is available, else CPU. No external API calls at request time.
Auth / rate limitingNone. Anyone who can reach the port can run inference.
ObservabilityOnly a print() of model-load time and total time per request.

7. The key design weakness in this version ("Act 1")

The model is loaded inside the request handler. Every call to /generate/text re-creates the pipeline and re-reads ~1.1B parameters into memory before generating anything. The printed log line [act1] model load: Xs, total: Ys exists to show you that the load time dominates the total.
  • Latency: seconds of loading before any token is generated.
  • Memory: concurrent requests each load their own copy, risking out-of-memory errors.
  • Wasted work: the weights never change, so loading them repeatedly is pure overhead.

Target design ("Act 2" - load once)

Load the pipeline once at application startup (FastAPI lifespan event, stored on app.state, or a module-level variable). The handler then only calls generate_text(pipe, ...). 
BEFORE (now)                               AFTER (recommended)
------------                               -------------------
request -> load model (slow)               startup  -> load model ONCE (slow)
        -> generate                        request  -> generate (fast)
request -> load model (slow) again         request  -> generate (fast)
        -> generate                        request  -> generate (fast)

8. Other design considerations

  • Concurrency: even with a single loaded model, concurrent generations compete for the same GPU/CPU. A lock, queue, or batching layer may be needed under load.
  • Input validation: temperature should be bounded (e.g. greater than 0, at most 2); invalid values currently surface as HTTP 500.
  • HTTP method: a POST with a JSON body suits long prompts better than GET query strings.
  • Streaming: returning tokens as they are generated (Server-Sent Events) would improve perceived latency.
  • Security: add authentication and rate limiting before exposing the service publicly.
  • Dev tooling: exclude the genaiservice venv from --reload watching so installs don't restart the server.
